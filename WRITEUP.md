# Rate Connect onboarding email: write-up

Alireza Pakseresht Koubijari · Email Development & Marketing Automation intern case study

## How I approached it

**I started with the brief, not the design.** I listed what you actually score: an email that matches the design, holds up in Gmail, Outlook and Apple Mail, works when you send it yourselves, and code someone else can change in six months. Every decision below goes back to one of those.

**I got the design as data, not as a picture.** You sent a `.fig` file rather than a Figma link, so Claude Code wrote a small script that decodes Figma's file format and prints every frame with its sizes, padding, gaps, colors and fonts. That became the spec. For each section, Claude Code checked that padding plus content added up to Figma's frame height, which showed, for example, that the banner has a fixed height and that the hero's headline sits in a nested frame with its own gap. I then went through the sums myself to verify them. At 700px the finished email is 1,256px tall, exactly like the Figma frame. Later I cross-checked the footer with Figma's MCP: every size, color and spacing matched, apart from two differences I had made on purpose (the icon's full circle, and a 2px transparent edge on the footer logo image that the padding compensates for). I compared the exported images with Figma's own exports, which is how I caught a cut edge and thin seams in the avatar.

**I decided the rules before building.** Classic Outlook draws emails with Word, so it's tables and inline styles, with Outlook's own versions of the rounded shapes. One media query switches to the phone layout below 600px. Apps that ignore it still get a layout that shrinks to fit. Classic Outlook ignores it too, and gets a fixed 700px layout instead (see the trade-offs below). Then section by section: build it, render it in Chrome and through Word, compare with Figma, move on.

**I questioned the design.** A few things looked off. I couldn't tell whether they were decisions or mistakes, so I corrected them and I'm flagging them: the trivago icon's circle was cut off at the top and bottom, the mobile logo wasn't centered, and the line under "Got more than one property?" ran out of its text box. While checking the logo, Claude Code also found empty space on its right side, which pushed it off-center.

**I tested where it matters.** A browser preview proves very little, so the email went to my own iPhone, Android phones and Windows PC, in light and dark mode. When dark mode broke, I didn't patch blindly: I built one test email with three or four candidate fixes per problem side by side, sent it to eight app setups, and kept the winners (`tests/RESULTS.md`). Then Email on Acid covered the apps I don't own, including Yahoo, Samsung Mail, Outlook on Mac and on phones, and Outlook on the web in dark mode.

**I asked the apps before fighting them.** After rounds of dark-mode workarounds, I asked whether the footer could simply stay the same in every mode. That led to `color-scheme: light only`, a setting the Gmail app has respected for Google accounts since a recent update (Dyspatch reported the change, and my own phones confirmed it). With it, the Gmail app stops recoloring the email for Google accounts (with an Outlook account inside the Gmail app it doesn't; see below). The earlier workarounds stay in as a fallback for app versions that don't respect it.

**I thought about the people after me.** Every sentence and button label is live text, written as one piece, so a translation script can find and replace it. That's why "Add a property" has square corners in classic Outlook: with its black text on white, a rounded Outlook button only stayed readable in dark mode with an image label, and an image can't be translated. The code explains its why, a checker catches the mistakes a browser hides, and the AMPscript has its own tests.

## How I made decisions

- **Find the cause before the fix.** Dark mode broke in a different place in almost every app. Instead of patching each one, I looked for what the bugs had in common. The color bugs all sat where something an app recolors (a background color, text) meets something it never recolors (an image, a VML shape), and that one rule decided every later fix.
- **Evidence over assurance.** Early on, Claude Code called a fix done before anyone had looked at it, and it didn't work. After that, a fix only counted as done once I had seen it working in the real app it was for.
- **Change one thing at a time.** Each test round set out to answer specific questions, so when something changed, I knew why. In round 3, Claude Code swapped the header's working gradient for a background image that wasn't uploaded yet, and the header broke. Since then, new fixes go on top of ones that work.
- **Trust real devices over testing tools, and check the tools themselves.** This is the one I'd most want you to know about. **Email on Acid showed the footer as an empty white box in dark mode on all five of its Gmail Pixel test phones (Pixel 6 to 10, Android 12 to 16; `screenshots/40` shows the Pixel 6). On a real Pixel 8 Pro with Android 17, on my own Android phone and on two other Android devices, the same email looks exactly right.** My best explanation is timing: the Gmail app (with a Google account) only started respecting `color-scheme: light only`, which tells the app not to recolor the email. That's the setting this email relies on. A testing tool can run an older Gmail version, or simulate dark mode its own way, and then it shows problems that real readers with an up-to-date Gmail never see. **So if your team's testing tools flag Android dark-mode problems in emails like this one, check them on a real, up-to-date phone before changing any code.** Otherwise you can end up "fixing" something that works and breaking it for real readers. I documented this one and left the code alone.
- **Make every trade-off visible.** Where email can't do what the design shows, I chose, and wrote down what each choice costs:
  - **700px width, kept as designed.** I stayed faithful to the design. The cost is in classic Outlook: it can't do "shrink, but never wider than 700px", so it gets a fixed 700px table, and in a reading pane narrower than that, the email doesn't shrink to fit.
  - **Each device's own system font, so SF Pro only on Apple.** SF Pro is Apple's system font. Apple's license for it is restrictive outside its own platforms, and even a freely licensed web font would be ignored by Gmail on the web and classic Outlook. So the email asks for "the system font": iPhones and Macs show SF Pro itself, exactly as designed, Windows shows Segoe UI and Android shows Roboto. The cost is a slightly different look outside Apple.
  - **"Light only" instead of a dark version.** The design has no dark mode, and recoloring broke it in almost every app. The cost: in new Outlook, which ignores the setting, the light sections still turn dark (readable).
  - **Square "Add a property" button in classic Outlook.** It's a plain cell with live text, so the label can be translated, and in dark mode Outlook recolors the cell and its text together, which kept this kind of button readable in my dark-mode test (row 1D). The cost: in that one app the button has square corners instead of the design's rounded ones.
  - **At most five rates for multi-property hoteliers, then "+ N more".** That keeps tip 2 short, and it guarantees that no portfolio can push the email past Gmail's 102 KB clipping limit, which would hide the footer and the unsubscribe link (without the cap, that would take about 800 properties). The cost is that big portfolios see their full list in Business Studio, not in the email.
- **Plan for missing data.** Every personalized value has an answer to "what if it's empty?", so no hotelier ever gets "Hello ," or a blank line.

## What broke, and what I did

- **Classic Outlook:** clipped digits in the circles, cropped icons, a thin line around the logo. All found by rendering through Word.
- **Dark mode:** the Gmail apps and both Outlooks recolored parts of the email. The fix is "light only", plus tiny background images and VML panels that hold the header and footer colors in Outlook.
- **Android:** a bigger text setting stretched the number circles into ovals, so they're images now.
- **Email on Acid:** T-Online's webmail deletes the parts hidden from Outlook, which took the number circles with them. A one-space change fixed it. Its Pixel test phones also show the footer as an empty white box (`screenshots/40`), but a real Pixel 8 Pro on Android 17, my own Android phone and two other Android devices show it correctly. That looks like a bug on their side, so I left it alone.
- **Not solved: the Gmail app with an Outlook account, on iPhone, in dark mode.** This one I don't know the best fix for, and it's one of my limitations. That setup ignores "light only" and drops the email's style block. It darkens the footer's white legal text but not the navy background, so the text becomes almost unreadable. I tested two fixes side by side (`tests/footer-variants.html`). Writing the blend layers directly on the text showed solid boxes instead, because this setup ignores blend modes. Light gray text stayed readable in both modes, but it moves the footer away from the design's white. I wasn't sure which trade-off you'd prefer, so I left the email as designed and I'm flagging it here.
- **Wrong turns**, all logged in `NOTES.md`: an Outlook rule that did nothing, and an outline Claude Code put on the trivago logo, which I then had it remove because you don't change a brand's logo.

## AMPscript

One property gives the email as designed. Several give a property count, one rate each (five at most, see above) and no "add a property" banner. Missing data never leaves a gap or a "Hello ,". The table and field names are my guesses, all in the logic block at the top of the file. I couldn't run it in Marketing Cloud, so I had Claude Code build a small test runner that runs the script against eleven test cases on my PC. It caught a preview that didn't match what the script really produces. Because a runner can only check what it assumes, I also had every function checked against Salesforce's AMPscript reference. That found two bugs the runner had missed: the loop counter was declared with `VAR`, which Salesforce says fails validation, and the commission rate was typed as a whole number, so 10.5% would not have imported. Then I ran it through Salesforce Labs' open-source AMPscript engine as a second opinion: all eleven cases agree with my runner. `AMPSCRIPT.md` has how I built and tested it, with screenshots. I also sent the finished emails for three sample hoteliers to my own inbox: one property, a very long property name, and more than five properties. All three displayed correctly.
