# Rate Connect onboarding email: build notes

This is the long version of `WRITEUP.md`: the main build bugs in one table, every place I moved away from the design, and the whole testing story. The dark-mode tests themselves are in `tests/RESULTS.md`.

Alireza Pakseresht Koubijari · Email Development & Marketing Automation intern case study

## Approach

I treated the Figma file as data rather than a picture. The design came as a `.fig` file rather than a Figma link, so Claude Code wrote a small script that decodes Figma's file format (a zip holding the design in Figma's own binary format) and prints every frame of the Desktop (700px) and Mobile (300px) designs with its size, padding, gaps, colors and fonts. That became the spec. For each section, Claude Code checked that padding, content and gaps added up to Figma's frame height, which showed where a frame had a fixed height or a nested gap. I then went through the sums myself to verify them. Later I had Claude Code cross-check the footer through Figma's MCP. Every size, color and spacing matched, apart from two differences I had made on purpose: the trivago icon is a full circle instead of the cut-off one, and the footer logo image carries a 2px transparent edge (107 by 33px instead of 103 by 29), which the padding above and below compensates for. At 700px the build is 1,256px tall, the same as the Figma frame.

- **Structure.** One fluid table, capped at 700px, with eight section rows. All visual styling is inline. The stylesheet holds only resets, the Gmail dark-mode text fix and one media query (600px), so a client that drops it still shows a fluid version of the desktop layout instead of a broken one.
- **Outlook on Windows.** It renders with Word, so it gets a fixed-width wrapper table, VML shapes for the rounded main button and the three number circles, VML panels that hold the header and footer colors in dark mode, and Segoe UI as its font. Every other app gets the circles as images, which phones cannot stretch and dark modes cannot recolor. Everything Outlook-specific sits in conditional comments.
- **Two files.** `email.html` keeps the design's placeholders and renders in any sending tool. `email-ampscript.html` is the same markup with AMPscript. `previews/` shows what the AMPscript produces for a single-property and a multi-property hotelier.

## Where the build leaves the design, and why

- **Font.** SF Pro is Apple's system font. Apple's license for it is restrictive outside its own platforms, and even a freely licensed web font would be ignored by Gmail on the web and classic Outlook (caniemail.com). So the font stack (`-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, Helvetica, Arial`) asks for each device's system font: SF Pro on iPhone and Mac, exactly as designed; Segoe UI on Windows; Roboto on Android. Classic Outlook is pinned to Segoe UI.
- **Problems in the Figma file itself.** Going through the file, I found a few things that looked off. I couldn't tell whether they were design decisions or mistakes, so I corrected them in the build instead of copying them, and I'm flagging them here so the designer can tell me if I got it wrong.
    - The small trivago icon next to "trivago Business Studio" sits in a circle whose top and bottom are cut off: it's a 15px circle inside a 14px frame. I exported the full circle.
    - On mobile, the trivago Rate Connect logo isn't centered; it sits about 13px left of center (the next point explains why). I moved it to the middle so it has the same space on both sides.
    - On mobile, the line under "Got more than one property?" is set to grow sideways instead of wrapping, so it runs out of its text box and becomes unreadable. I let it wrap, centered, at the right size.
    - The logo component is 254px wide but the logo itself is only 228px, so placing the component in the center shows the logo 13px left of center. The build's image is the 228px logo centered on a 260 by 41px white tile, so it sits exactly in the middle.
- **Support links on mobile.** The design puts them in a full-width row under the avatar. Matching that needs duplicated hidden content or floats, so the build keeps one structure and stacks them beside the avatar.
- **Color.** The hero subtitle is black at 70% opacity. Classic Outlook ignores `rgba()`, so it is flattened to `#454a4d`.
- **"Add a property" in classic Outlook: square corners, on purpose.** I thought about translation and dark mode together. Rounded corners in classic Outlook need VML, Outlook's own drawing code. Its dark mode turns black text white on a VML shape it never recolors, so the label disappears, and the only fix I found was an image label, which can't be translated. A plain table cell with live text gets recolored together with its text, so it stays readable (the same kind of cell passed test row 1D), and it translates and grows with any label. The price is square corners in that one app; every other app keeps the rounded design. I chose translatable over rounded. The link's border makes the whole button clickable, and in Word's engine it measures 122 by 36px (the design is 124 by 36).
- **Width.** The design is 700px, wider than the usual 600px. It is kept as drawn. The cost: classic Outlook gets a fixed 700px table and will not shrink it for a narrower reading pane.
- **Dark mode.** The design is light only, and the email says so with `color-scheme: light only`. Apple Mail respects it, Gmail on the web never recolors email content anyway, and the Gmail app respects it since a recent update for Google accounts (reported by Dyspatch, confirmed on my phones). The Gmail app with an Outlook account does not (see "Not solved" below). Classic and new Outlook ignore it. Classic Outlook keeps the colors through VML panels; new Outlook recolors some sections. The color bugs all had one cause: something the app recolors (a background color, text) next to something it never recolors (an image, a VML shape). The fixes were picked from a test sheet sent to eight app setups (`tests/RESULTS.md`). Known leftovers: new Outlook still recolors the light sections (hero, banner, body) in dark mode and turns the footer slate gray, all readable; classic Outlook shows the footer links white.
- **Footer logo.** The plain trivago logo, never altered. An earlier build gave it a navy outline so it stayed readable where apps turned the footer light; that changed the brand asset, so it was removed. The footer now stays navy on my own devices everywhere except new Outlook, where it turns slate gray and the white logo still reads.

## Testing

Done: Chrome at 700, 600, 375, 320 and 300px; Word's HTML engine, which is what classic Outlook renders with; a copy with the stylesheet removed; and `tools/preflight.py`, which Claude Code checked against deliberately broken copies of the email to make sure it catches each mistake (the copies aren't kept in the folder).

Real inboxes: I sent the email to my own accounts with `tools/send_test.py`, so it arrived exactly as written. Light mode was correct in Gmail on the web, the Gmail app, Apple Mail, and classic and new Outlook (`screenshots/05` to `08`, `11`, `12`, `17` and `18`; the dark-mode and after-fix shots are in the same folder, named by app and mode; "after-fix" means after the first fixes, before "light only"). Dark mode broke in the Gmail app and both Outlooks. To fix it I sent one test sheet, `tests/dark-mode-variants.html`, with three or four candidate fixes per problem, and checked it in eight setups: Gmail on the web, the Gmail app on iPhone (with a Google account and with an Outlook account), the Gmail app on Android, Apple Mail, classic Outlook, new Outlook and Outlook on the web. The results and lessons are in `tests/RESULTS.md`, the 51 screenshots in `tests/screenshots/`. The final build uses the winners. Two more rounds in real inboxes found Android and new Outlook problems, a missing upload and the logo outline; all are fixed (`tests/RESULTS.md`, rounds 3 and 4). Since then, the only change for classic Outlook is "Add a property", which became a square button with live text (see above).

In the final real-inbox round, the build looked as designed in light mode everywhere I tested, and in dark mode in Gmail on the web, the Gmail app on iPhone and Android (Google accounts), Apple Mail and classic Outlook. Three changes came after that: the T-Online spacing fix (confirmed in Email on Acid), the square "Add a property" button in classic Outlook (checked in Word's engine), and the gradient footer (round 8). Then I sent the email to my own devices again, and it still looks as designed. The remaining differences are new Outlook recoloring the light sections and showing the footer slate gray in dark mode (still readable), and classic Outlook showing the footer links white instead of light blue.

Before those last changes, I ran it through Email on Acid (now part of Mailgun), which covers apps I don't have, including Yahoo, Samsung Mail, Outlook on Mac and on phones, and Outlook on the web in dark mode. Everything looked right there except two things (`tests/RESULTS.md`, round 6):

- **T-Online's webmail** didn't show the number circles. T-Online deletes everything inside the `<!--[if !mso]><!-->` wrappers that hide things from classic Outlook, and the circle images sit in one. The HTML buttons do too, so they were probably missing as well. Writing the wrapper with a space inside (`<!--[if !mso]><! -->`) is the known fix. Chrome and Word render exactly as before, and the checker now fails on the old spelling. A second Email on Acid run confirmed it: T-Online now shows the circles.
- **The Gmail app on Pixel 6 to 10 in dark mode** showed the footer as an empty white box, with the logo, text and links all gone (`screenshots/40` shows light and dark side by side; `39` is Email on Acid's overview of its Pixel results). It was still there in a second run. But on a real Pixel 8 Pro with Android 17, on my own Android phone and on two other Android devices, the footer is fine. So at first I didn't change anything: changing code that works on real phones to suit one test setup felt like the bigger risk. But a reviewer who opens Email on Acid before a real phone would see a broken footer, so I looked again. That Gmail version ignores "light only" and inverts the whole email, so the navy footer turns white and the white logo and text disappear into it. In the same screenshot, "View your campaign" stayed blue, and it's the only thing with a CSS gradient background, which Gmail doesn't recolor. I tested three footers side by side in Email on Acid (`tests/footer-android.html`, round 8). A gradient alone kept the footer navy on its Pixel phones and looked right in every other app there. A gradient plus the old navy image didn't work in a lot of them. The cost: new Outlook and Microsoft 365 in the browser ignore gradients and show the footer slate gray in dark mode (`screenshots/41`), readable but not navy. Afterwards I sent the email to my own devices again, and it still looks right on them.

## Not solved: the Gmail app with an Outlook account, in dark mode

This is one of my limitations: I don't know the best way to fix it.

On my iPhone, with my Outlook account added to the Gmail app, dark mode makes the footer's legal text almost unreadable. This setup ignores `color-scheme: light only` and drops the email's style block. It darkens the white text but not the navy, because at the time of the test the navy was held by a background image, and apps never recolor images. Since round 8 the navy comes from a CSS gradient instead. That doesn't change the cause: the text turns dark because this setup drops the style block that keeps it white. The "Update preferences | Unsubscribe" links get dim too, though they stay readable. My dark-mode test sheet had already shown this in row 3C (`tests/RESULTS.md`), but at the time it wasn't known whether this setup respects "light only". It doesn't.

I tested two fixes side by side in one email (`tests/footer-variants.html`, results in `tests/RESULTS.md`, round 7):

- **Blend layers written directly on the text**, switched off again by the style block in every app that keeps it. This setup keeps the layers' black background but ignores the blend mode, so the text sat in solid boxes: white boxes in dark mode, black in light mode. Rejected.
- **Light gray legal text (`#a3abb8`) instead of white.** This setup leaves mid-gray text alone, so it stayed readable in dark and light mode. It's a visible change from the design's white, though.

I prepared a second test with lighter and lighter grays, to find the lightest one this setup still leaves alone (`tests/footer-shades.html`), but I haven't sent it. I left the email as designed, because I'd want to know how much this setup matters to your hoteliers before changing the footer for everyone. It's one of my questions for your team below.

## AMPscript (tested locally, not yet in Marketing Cloud)

There's no free Marketing Cloud account, so I had Claude Code build a small test runner, `tools/ampscript_run.py`. It executes the part of AMPscript this email uses against twenty-four test cases in `tests/ampscript/cases.json`: one, two, five, six and seven properties; missing data (no name and no data, data only on the sendable row, a fallback rate without a name, no hotelier ID, a missing rate, a rate of 0, a wrong table name); messy data (spaces around or instead of a name, an ID, a property name or a rate, an ID in lower case, `&` and `<` in names, a rate stored with "%", a property without a name in a list); and two rules (umlauts in the A to Z sort, the lookup winning over the fallback columns). For each one, it checks what the email must and must not say.

All twenty-four pass, and a planted bug in the banner rule, the sort order, a function name or an `ENDIF` makes them fail. It found one real problem: the multi-property preview had been edited by hand and listed the properties in a different order than the script's A to Z sort. The previews are now the runner's real output.

Later I noticed that a name of only spaces would get past the empty check and print "Hello ,", because the script trimmed the name only after checking it. Five new cases showed the same gap for the hotelier ID, the fallback property name and rate, and the property rows, and all five failed. Now every value is trimmed first and checked after, and they pass. A review by Claude Code then found three more data problems: `&` and `<` in names broke the output, a rate stored as "12%" printed "12%%", and a property without a name in a list printed ": 12%". Names are now escaped, a stored "%" is dropped, and a nameless property shows as "Unnamed property" (a label, not a hidden line, so the list and "+ N more" still add up to the count in the intro). Each fix has a test case that failed before it.

The runner can also build one finished email per hotelier from a small sample database (`tests/ampscript/demo/`). I sent three of them to my own inbox (one property, a very long property name, and more than five properties) and all three displayed correctly. That shows the output works in a real inbox; it isn't a Marketing Cloud run. The runner imitates documented behavior; the final check is Preview and Test in Marketing Cloud, and `--csv` writes the same cases as data extensions to import there. One case differs slightly: "no hotelier ID column" becomes an empty `hotelier_id` value in the CSV, because a data extension has one set of columns for all rows. README.md has the steps for that test.

The runner only proves the script does what the runner thinks AMPscript does. So I also had Claude Code check every function and keyword the script uses against Salesforce's AMPscript reference. That found two real problems the runner had missed. The loop counter `@i` was declared with `VAR`, and Salesforce's reference says that "will result in a validation or runtime error". It's removed now, and the runner now fails on it. And the data spec gave `commission_rate` the Number type, which in Marketing Cloud only takes whole numbers, so a 10.5% rate would have failed the import. It's Text now. The check also confirmed the rest: `AttributeValue()` returns null instead of failing the send, `LookupOrderedRows()` with 0 returns every row up to 2,000 and ignores case, and `Field()` fails on an unknown column unless told not to. Then Claude Code and I ran the email through Salesforce Labs' open-source AMPscript engine (AMPscript Core), which doesn't share my runner's assumptions. With two changes to a test copy, both for gaps in the engine (it has no `LookupOrderedRows()`, and it crashes comparing a `Subtract()` result with a number), all twenty-four cases agree with my runner word for word. The email itself didn't change for anything the engine found. `AMPSCRIPT.md` has the whole story, with screenshots.

The script reads the hotelier from the sendable data extension and looks up their properties in a second one. One property gives the email as designed. Several give a property count in the intro, one rate per property (capped at five to keep tip 2 short; the cap also guarantees that no portfolio can push the message past Gmail's 102 KB clipping limit, which without it would take about 800 properties), and no "add a property" banner. Missing data never leaves a gap: no name gives "Hello,", no rate removes the line. The lookup returns at most 2,000 rows, so a hotelier with more properties than that would be undercounted. The table and field names are my assumptions: the table name is in the config block at the top of the script, and the field names are in sections 1 and 2 right below it, plus the property loop in tip 2. Whether the banner should show for single-property or multi-property accounts is a business rule I would confirm; it is one line to flip.

## How I used AI

I worked mostly in Claude Code. I tried bringing Cursor into the workflow as well, but I was on its free plan and reached the usage limit quickly; my Claude Code plan was paid, so that is where most of the work happened. I gave it the brief and the Figma file and asked it to do the task, document how, and teach me the method. It decoded the `.fig` file into a spec, exported the vector artwork to PNG, wrote the HTML and AMPscript, and drove Chrome and Word for the render tests.

What I would stress is that its first version looked correct in a browser and was wrong in Outlook in three places, and its first dark-mode fixes were called done before they had been seen working. None of those were found by reading the code; all were found by rendering it, in the end in real inboxes on my own devices. It also guessed trivago's Business Studio address from memory and got it wrong until a search corrected it. The decisions under "Where the build leaves the design" and the banner rule are the calls I would expect to be challenged on.

## Things I'd like to ask your team

- **Dark mode.** How do you handle it? Do you have dark-mode colors in your design library, or do you keep emails the same in light and dark mode? I tried several approaches, and dark mode broke differently on almost every platform, which is why I ended up with light only. In Apple Mail and the Gmail app with a Google account, that's also what keeps the navy footer from being recolored.
- **Spam.** Do you plan for emails arriving in spam? Each app treats spam differently and loads images differently there. My own test sends from a personal Gmail landed in spam, where images were blocked, so the alt text had to carry the email.
- **Priorities.** Which apps matter most for your hoteliers? Is it Gmail first, then Outlook, then Apple Mail, or something else? And how far back should I go: which devices and app versions do you support, and which do you ignore? Email on Acid found problems only in T-Online's webmail, which I fixed, and a footer bug on its Pixel test phones that real phones don't show, which I fixed anyway in round 8. T-Online is probably worth it for German hoteliers, but I don't know where you draw the line. That decides where the testing time goes.
- **The Gmail app with a non-Google account.** How many of your hoteliers read Gmail with an Outlook or other account? That decides whether the footer's legal text should be light gray (`#a3abb8`) for everyone (see "Not solved").
- **Translation.** I made the email instantly translatable, every sentence and label as live text, and it cost the rounded corners of the "Add a property" button in classic Outlook. Is that the trade-off you'd make, or do you create translated images for each language?

## What I'd do next

- One source for both builds (MJML or Marketing Cloud content blocks) so they cannot drift apart.
- Finish the localization pass. Every visible sentence is now one whole piece of text, so a translation script can find and replace it: 25 strings plus 5 alt texts (the AMPscript version adds one fallback label, "Unnamed property"). "View your campaign" and "Add a property" appear twice (the Outlook copy and the HTML copy), so replace every occurrence. I tried a German draft: the layout holds at 320px and the main Outlook button still fits, and "Add a property" is live text everywhere now, so it translates too. The open part is real German copy from trivago.
- Confirm the data model and the banner rule with the team, then run the AMPscript in a real preview.
- An accessibility pass. Two color pairs in the design are below the WCAG AA contrast ratio of 4.5:1 for small text: the gray `#8d8d8b` links on white (3.3:1) and white on the `#0088d9` button (3.8:1). The same blue on white is also used for the support link. The build keeps the design; I would raise it with the designer.
